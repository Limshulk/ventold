#### CB-1: `ic_event_bus::subscribe()` uses `= 0` instead of pure virtual

**File:** [ic_event_bus.hpp](file:///c:/dev/vent/source/vent_engine/_vent/core/ic_event_bus.hpp#L70)

```cpp
virtual auto subscribe(...) -> subscription_id = 0;  // BUG: initializes return value to 0, not pure virtual
```

This is **not** a pure virtual declaration. `= 0` on a non-void return type means "default-initialize the return value to 0". This makes the class non-abstract for this method. The correct syntax is `= 0` at the end of the declaration, but the `[[nodiscard]]` attribute + return type makes this parsed differently by some compilers. **This will compile but is semantically wrong** — it should match the pattern used by all other pure virtual methods in the codebase.

**Fix:** Confirm the intent is pure virtual and use the unambiguous form:
```cpp
virtual auto subscribe(...) -> subscription_id = 0;
```
Actually, looking more carefully: this IS valid pure virtual syntax in C++ regardless of return type. The `= 0` at the end of a virtual function declaration always means pure virtual. My mistake — this is actually correct. **Withdrawing this finding.**

#### CB-2: `log_buffer_iterator` – potential buffer overrun and UB

**File:** [accessors.cpp](file:///c:/dev/vent/source/vent_engine/modules/core/src/_vent/accessors.cpp#L90-L122)

The `log_buffer_iterator` is a custom output iterator used by `format_and_log()`. Two problems:

1. **`*result.ptr = '\0'`** — after `std::vformat_to` finishes, `result` is the return value of `vformat_to`, which is an `Out` iterator (i.e., `log_buffer_iterator`). But `result.ptr` may point past the end of the buffer if the formatted string exactly fills it. The null terminator is written to `buffer + sizeof(buffer) - 1` (the last valid position) or earlier, but if the output is exactly `4095` chars, `ptr` points at `buffer[4095]` and writing `'\0'` there is fine. However, if `vformat_to` writes more than 4095 chars, the `if (ptr < end)` guard silently drops chars but `result.ptr` will be `== end`, and `*result.ptr = '\0'` writes to `buffer[4095]` which is correct. **Actually safe but very fragile.** The iterator semantics are also non-standard — `operator=` does double duty as both dereference-assign and increment, and `operator*` returns `*this`, which is unusual.

2. **The struct is defined inside the `vent` namespace but not in an anonymous namespace or marked `static`.** It pollutes the `vent` namespace with an implementation detail.

**Fix:** Move into an anonymous namespace, or better, use `std::string` + `std::vformat()` to avoid the 4096-byte stack buffer entirely (which the existing `// todo` comment already notes is problematic).

#### CB-3: `thread_registry::exit_thread()` causes UB with `std::thread`

**File:** [thread_registry.hpp](file:///c:/dev/vent/source/vent_engine/modules/core/public/core/thread_registry.hpp#L82-L90)

`spawn_thread()` creates a `std::thread` and the lambda calls `exit_thread()` which calls `ExitThread(0)` (Windows) or `pthread_exit(nullptr)` (Linux). **This is undefined behavior** when using `std::thread`:

- `std::thread` expects its callable to return normally. Calling `ExitThread`/`pthread_exit` from within a `std::thread` skips C++ destructor unwinding for thread-local objects, RAII guards, and the `std::thread` internal state.
- The returned `std::thread` object is never joined or detached in this code (the caller is expected to manage it), but if `exit_thread()` kills the thread before the caller can join, the `std::thread` destructor will call `std::terminate()`.

**Fix:** Remove `exit_thread()` entirely. Let the lambda return normally. The thread will exit cleanly through `std::thread`'s internal machinery.

#### CB-4: `g_no_async` check in `log()` accessor prevents modular log system from ever being used in debug builds

**File:** [accessors.cpp](file:///c:/dev/vent/source/vent_engine/modules/core/src/_vent/accessors.cpp#L45-L58)

```cpp
VENT_API auto log() -> ic_log* {
#ifdef VENT_DEBUG
    return &fallback_log::instance();  // ALWAYS returns fallback in debug!
#endif
    // ... real log system lookup (dead code in debug) ...
}
```

The `#ifdef VENT_DEBUG` block has an unconditional `return`, making the real log system lookup unreachable in debug builds. This means:
- Debug builds **never** use the modular log system (file logging, etc.).
- This seems intentional (for synchronous output), but is undocumented and surprising.

**Fix:** Document this clearly with a comment, or make it a runtime flag like `g_no_async` does for the job system.

#### C-1: Math library functions should be `constexpr` where possible

**Files:** [vec3.hpp](file:///c:/dev/vent/source/vent_engine/_vent/math/vec3.hpp), [vec4.hpp](file:///c:/dev/vent/source/vent_engine/_vent/math/vec4.hpp), [mat4.hpp](file:///c:/dev/vent/source/vent_engine/_vent/math/mat4.hpp), [math.hpp](file:///c:/dev/vent/source/vent_engine/_vent/math/math.hpp)

**AGENTS.md rule:** *"always use `constexpr` or `consteval` and compile-time computations where possible."*

Currently all math operations use `inline` but not `constexpr`. The constructors, operators, `dot()`, `cross()`, `length_sq()`, `identity()`, `translate()`, `scale()`, `operator*` etc. can all be `constexpr`. Only `sqrt`/`cos`/`sin`/`tan`-dependent functions cannot (until C++26).

**Fix:** Add `constexpr` to all constructors, operators, and functions that don't use transcendentals.
